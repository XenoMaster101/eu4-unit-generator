# eu4unitgen — Technical Specification

Target: EU4 1.37.5 (verified against `release_1.37.5`, rev `835bfdf8`). Scope now: **land units only** (infantry, cavalry, artillery, 4 sprite tiers each). Later: ships, generals/advisor portraits, city models.

Items marked **UNVERIFIED** are not yet confirmed against the user's install or in game. Phase 0 confirmed everything not marked. The machine-readable record of the vanilla chain is `src/eu4unitgen/library/base_models.json`, generated by `library/scanner.py`.

---

## 1. Goal

For a given nation (tag) and graphical culture, the app generates every file EU4 needs to show that nation's land units on the map, validates the whole dependency chain, and exports into a mod folder. It works on two levels:

- **Script level (deterministic):** entities, pdxmesh definitions, sprite packs, pack order, unit definitions, tech unlocks, localisation, country/culture wiring.
- **Asset level:** textures (recolour, pattern overlay, spec masks) and meshes (retexture, kitbash onto vanilla skeletons via headless Blender). New rigged models from scratch are out of scope.

---

## 2. The EU4 land-unit file chain

Every map unit is an **entity**. The entity points to a **pdxmesh** (a named model). The pdxmesh points to a **.mesh** file, which names its **textures**. The pdxmesh also maps **animation ids** to **animation types**, and each type points to an `.anim` file. Entity states pick an animation id. Entities list **attachments** (weapons, riders on horses, gun crews). A **sprite pack** tells the game which entities a country uses at each of the 4 tech tiers.

| Layer | Location (vanilla) | Purpose | Links to |
|---|---|---|---|
| Mesh | `gfx/models/Units/*.mesh` | Geometry, skeleton, material (shader + texture names), locators | DDS files |
| Textures | same folder as the mesh | Colour, normal, specular + country-colour mask | — |
| Animation clips | `gfx/models/Units/animation/*.anim` | Skeletal clips | Skeleton in mesh |
| Animation types | `gfx/models/Units/animation/animation.asset`: `animation = { name = "<type>" file = "<x>.anim" }` | Script name for a clip. `file` is relative to the `.asset`'s folder | `.anim` |
| pdxmesh | `interface/assets/*.gfx`, inside a top-level `objectTypes = { ... }` | Script name for a mesh + `animation = { id = ... type = ... }` map + `scale` | `.mesh`, animation types |
| Entities | `gfx/entities/*.asset` | `TAG_INFANTRY_1` etc.: pdxmesh + states + attachments | pdxmesh, other entities |
| Sprite packs | `gfx/sprite_packs/*.txt` | Which entities a tag or graphical culture uses per tier | Entities |
| Pack order | `gfx/sprite_packs_order/*.txt` | `pack_name = number` | Sprite packs |
| Graphical culture | `common/graphicalculturetype.txt`; country file `graphical_culture = xxxgfx` | Default unit/portrait/city set | gfx sprite pack + default entities |
| Unit stats | `common/units/*.txt` | type, unit_type (tech group), maneuver, pips | Tech + loc |
| Tech unlock | `common/technologies/mil.txt` | `enable = <unit>`, `sprite_level` | Units |
| Localisation | `localisation/*_l_english.yml` | `<unit>:` and `<unit>DESCR:` | Units |

Base game and DLC both put pdxmeshes in `interface/assets/*.gfx`; DLC116 ships `interface/assets/scanup_DAN.gfx` next to `gfx/entities/scanup_DAN_units.asset`. No vanilla or DLC file defines a pdxmesh inside `gfx/entities`.

**Project file layout (follows vanilla):**
- `interface/assets/<prefix>_<tag>.gfx`: pdxmeshes in `objectTypes = { }`
- `gfx/entities/<prefix>_<tag>_units.asset`: entities
- `gfx/models/Units/<prefix><set>_<role>_<tier>_<kind>.dds`: derived textures, **in the mod's copy of the vanilla mesh's folder** (meshsettings texture names resolve there only; §4, in-game test 4)
- `gfx/models/units/<prefix>_<tag>/<prefix>_animations.asset`: animation types, only for new `.anim` clips. Vanilla has `.asset` animation files in several `gfx/models/` subfolders (`Units/animation`, `ships`, `Mapitems`, `animated_mapobjects`). **UNVERIFIED:** that the engine loads a mod-added animation `.asset` from a new subfolder. Reuse vanilla animation types whenever the vanilla skeleton is kept.

Entity names and pdxmesh names are **separate namespaces**. Vanilla has an entity `DAN_INFANTRY_2` and a different pdxmesh also named `DAN_INFANTRY_2`. `naming.py` still gives generated pdxmeshes a `_mesh` suffix so the two can't be confused.

### Sprite levels (vanilla, confirmed)
| Tier | sprite_level | Vanilla MIL tech | Year |
|---|---|---|---|
| 1 | 1 | 0 | 1350 |
| 2 | 2 | 12 | 1557 |
| 3 | 3 | 21 | 1674 |
| 4 | 4 | 26 | 1745 |

Level 5 (MIL 30, 1805) is commented out in `mil.txt`. A total conversion controls `mil.txt` and can remap tiers to its own eras, but there are still only 4 land tiers.

The game shows **one model per army**, chosen by the dominant unit type, so every nation needs all 3 types × 4 tiers = **12 root entities**, plus attachment entities.

## 3. Naming, versions, sprite packs

- Tag entities: `TAG_INFANTRY_1..4`, `TAG_CAVALRY_1..4`, `TAG_ARTILLERY_1..4`; riders `TAG_CAVALRY_n_rider`.
- Graphical-culture defaults: `<gfx>_INFANTRY_n`, `<gfx>_CAVALRY_n`, `<gfx>_CAVALRY_n_rider`, `<gfx>_ARTILLERY_n`; cannons `<gfx>_ARTILLERY_n_cannon`. Western artillery tiers 2–4 clone `westerngfx_ARTILLERY_1` as `westerngfx_ARTILLERY_n_generic`.
- DLC variants carry suffixes (e.g. `_evup`, `_generic`).
- Cloning: `entity = { clone = "SRC" name = "NEW" ... }`. Fields given on the clone override the source (e.g. `pdxmesh`). DLC116 combines `clone` and `version` in one entity.
  **UNVERIFIED, moot for the generator** (it emits no clones): whether a clone's `attach` blocks replace the source's by attach `name` or are added. Vanilla always restates the named attach (`name = "rider"`, `name = "gunman"`) on clones.
- **Clones resolve at load time, in load order (confirmed in game, 2026-10-14).** The parent must already be loaded when the engine reaches the `clone =` line. Load order for `gfx/entities/*.asset` is file name order (base game and DLC files interleaved; a mod file takes its own name's slot), then top to bottom in each file. A mod file named `hr_*.asset` loads before `western_units.asset`, so `clone = "westerngfx_CAVALRY_1"` fails with `Couldn't find parent clone entity`. This model fits all 4,760 vanilla + DLC clones on 1.37.5; the 7 whose parent lives in another file all point at an earlier-sorting file (`wonup.asset` → `western_units.asset`, `_musup_units.asset` → `_hindup_units.asset`). Paradox names some files `_*.asset` so they load first. **UNVERIFIED:** whether the name order is case-sensitive (no vanilla file name tells them apart; the validator uses lowercase).
- `attach` targets and `pdxmesh` names are **not** resolved at load: infantry attaching `western_musket` (defined in `weapons.asset`, after `hr_*`) works in game.
- **The generator never emits `clone =`.** Every generated entity is a full definition: the base entity's resolved `pdxmesh`, live states and attaches, with the named attach (`rider`, `gunman`) swapped for ours. The `clone_order` validator rule rejects any generated clone whose parent isn't loaded before it.

### version
- Vanilla base-game entities have **no** `version` line.
- DLC116 redefines `DAN_INFANTRY_1`, `DAN_CAVALRY_1`, etc. with `version = 4` to replace the base-game definitions. `weapons.asset` uses `version = -1` on an entity it deliberately duplicates.
- The project uses a project-wide `version` (default 20) on every generated entity. Collisions log `Set a higher version on entity X`.
- **UNVERIFIED, not covered by the Phase 1 tests:** that a missing version counts as 0 (Phase 0 only shows `version = 4` beating no version), and which definition wins on a tie. Generated entity names are new (`version_collisions` checks), so neither affects Phase 1 output.

### Sprite packs
- **Since 1.30, sprite packs assign entities to tags** via `country_trigger`. Indices `0–3` = tiers 1–4.
- **Partial packs are confirmed:** `dlc116_DAN_sprite_pack` lists indices 0, 2, 3 only.
- **Graphical-culture packs.** Vanilla wires each culture's defaults through a pack in `gfx/sprite_packs/+00_base_sprites.txt`:
  ```
  westerngfx_sprite_pack = {
      country_trigger = { always = no }
      graphical_cultures = { westerngfx }
      sprite_infantry = { 0 = westerngfx_INFANTRY_1 ... }
      ...
  }
  ```
  **A new graphical culture needs its own default `<gfx>_INFANTRY/CAVALRY/ARTILLERY_1–4` entities plus a gfx sprite pack like this one**, or countries without a tag pack have no models. The generator always emits a TAG set, a gfx-culture default set and both packs.
- **Pack order.** Base-game packs (including `dan_base_sprite_pack` and all gfx packs) have **no** entry in `sprite_packs_order`. The vanilla order file says the default is 0 and *"anything higher will take priority"*. Its bands are 0 gfx culture, 10 culture groups, 20 culture group, 30 primary cultures, 40 primary culture, 50 tags, 60 tag, 70 more specific. DLC goes up to 100 (`dlc116_DAN_sprite_pack = 100`).
  - The generator writes an order entry for every **tag** pack. The default is 110 (configurable), so a tag pack beats any vanilla or DLC pack whose trigger might also match a total-conversion nation. The validator warns when a vanilla or DLC pack with a higher number could match the same country.
  - gfx-culture packs get no order entry, matching vanilla.
  - **Confirmed in game (2026-10-14, test 3): the higher order wins.** Two packs with the same trigger (`tag = HDA`): at A 110 / B 111 HDA showed B (asiangfx); swapped to A 111 / B 110 it showed A (western). File and pack names didn't decide (`hr_macedonian_test_*` vs `hr_priority_test_*`, same result both ways).
- **Fallback order, confirmed in game (2026-10-14, test 3, 1.37.5):** a country uses the highest-order sprite pack whose `country_trigger` matches it; failing that, **its graphical culture's pack** (`graphical_cultures = { ... }`). **`TAG_*` entity names alone do nothing**: BAL with full `BAL_INFANTRY/CAVALRY/ARTILLERY_1–4` entities and no pack showed its graphical culture's (indiangfx) models. So every generated TAG set needs its tag pack, which the generator always writes.
  - (a) BTS, no pack and no `BTS_*`: its own africangfx models (gfx-culture pack).
  - (b) BAL, `BAL_*` entities, no pack: indiangfx, not the entities.
  - (c) QTO switched to the new `hellenicgfx`, covered only by the generated `hellenicgfx_sprite_pack`: showed the hellenicgfx default set (muslimgfx copies in that test). **A new graphical culture with its own default set and gfx pack works.**

### Graphical culture list
`common/graphicalculturetype.txt` is a bare list of names, one per line, with no braces or keys (e.g. `westerngfx`). It is a single file, not a folder. At export the generator writes it into the mod by reading the user's vanilla list and adding the new names. It is never stored in the repo.
The mod's copy (vanilla list + `hellenicgfx`) works in game: QTO used `hellenicgfx` (test 3), and error.log had nothing about graphical cultures. **UNVERIFIED, moot:** whether the copy replaces vanilla's file or merges with it. Both give the same list, because the copy contains every vanilla name.

## 4. Shaders, textures, country colours

Shaders (code in `gfx/FX/pdxmesh.lua`):

| Shader | Use |
|---|---|
| `PdxMeshColor` | Most generic units. **Spec map RGB = country primary/secondary/tertiary colour masks.** |
| `PdxMeshStandard` | Fixed-colour meshes: weapons, cannons, the artillery base, and some nation-specific uniforms (`DAN_01.mesh`, `DAN_04.mesh`) |
| `PdxMeshTextureAtlas` | Prints country flag, UV range 0.05–0.95 |
| `PdxMeshSnow`, `PdxMeshAlphaBlend`, `PdxMeshAlphaBlendNoZWrite`, `PdxMesh_NoFoW_NoTI`, `Collision` | Special cases |

**Nation-specific meshes may not take country colours.** DAN's tier 1 and 4 uniforms use `PdxMeshStandard`; the generic western meshes (`western_generic_01–04_type1`, `cavalry_horse`, `cavalry_horse_03`) use `PdxMeshColor`. `base_models.json` records `shader` and `uses_country_colour` for every pdxmesh. **Recolour and kitbash bases default to the graphical culture's generic meshes** (`recolour_bases` in `base_models.json`), not to nation-specific ones. Cannons are `PdxMeshStandard` and never take country colours.

### Texture facts (confirmed, western chain)
- Texture names inside the `.mesh` material are **bare file names**, resolved in the mesh's own folder.
- Formats: **diffuse DXT1, normal DXT1, specular DXT5**. Full mip chain; no DX10 header. Infantry textures and horse normal/spec maps are 512×512. Horse diffuse maps and all three cannon maps are 256×256. The weapon sheet is 512×256. The artillery base uses 4×4 `nospec.dds`/`nonormal.dds` placeholders.
- Default DDS output: copy the base texture's format and size (read from `base_models.json`/the header). That means BC1/DXT1 for diffuse and normal and BC3/DXT5 for spec, **not sRGB**, no DX10 header, full mip chain.
- Spec map **alpha = gloss**. Existing spec maps contain zero-alpha areas that still hold colour, so don't treat alpha 0 as empty.
- Gloss presets from community trial and error: ~1–4% matte, 5–10% cloth, 10–16% metal, 17–20% mirror; above that, extreme shine. UI presets: 3%, 8%, 13%.
- Because PdxMeshColor paints country colours automatically, recolouring a nation on a PdxMeshColor base often needs **no texture work**. Texture work is for new uniform patterns, insignia or fixed colours.
- New textures need a pdxmesh whose material names them. **Confirmed (in-game test 4, 2026-10-14): a pdxmesh `meshsettings` block retextures a vanilla unit mesh**, no mesh copy needed:
  ```
  pdxmesh = { name = "hr_mac_infantry_1_mesh"  file = "gfx/models/Units/western_generic_01_type1.mesh"
      animation = { ... all of the base pdxmesh's ids ... }  scale = 0.5
      meshsettings = { name = "western_generic_01_type1Shape" index = 0
          texture_diffuse = "hr_mac_infantry_1_diffuse.dds" texture_normal = "western_generic_01_type1_normals.dds"
          texture_specular = "western_generic_01_type1_spec.dds" shader = "PdxMeshColor" shader_file = "gfx/FX/pdxmesh.shader" } }
  ```
- **meshsettings texture names are bare file names, resolved in the `.mesh`'s folder.** The engine prefixes the folder to whatever is written: full paths became `gfx/models/Units/gfx/models/units/hr_.../..._diffuse.dds` and `gfx/models/Units/gfx/models/Units/western_generic_02_type1_spec.dds` in error.log and the unit rendered black. Generated DDS go into the mod's copy of that folder, and a generated name must never equal a vanilla/DLC texture there (it would replace that texture for every nation). Rules `texture_paths`, `mesh_settings`, `dds_format`.
- **How PdxMeshColor uses the spec map** (vanilla `gfx/FX/pdxmesh.shader`, `PixelPdxMeshColor`): `col = lerp(col, col * spec.r * Primary, spec.r)`, then the same for `spec.g`/Secondary and `spec.b`/Tertiary; specular highlight intensity = `spec.a * 2`. So the diffuse under country regions is a neutral grey that the country colour multiplies; a coloured diffuse there tints the country colour. PdxMeshStandard ignores spec RGB.
### Mod scripts that recolour countries (in-game test 9, 2026-10-16)
- **Confirmed (A/B):** Victoria's Secret includes "Color Your Subject" (CYS). Its `on_startup` (`common/on_actions/cys_on_actions.txt`) sends the player `cys.1` (`events/CYSEvets.txt`), whose `immediate` runs `every_country = { limit = { is_colonial_nation = no is_dynamic_tag = no } restore_country_color = yes }`. With it, MAC's units showed MAC's **map colour** (235 200 0, from `common/countries/Macedonia.txt`) as the primary unit colour (yellow hoplon, olive cloth = yellow on the grey diffuse) and a wrong secondary (blue trousers), not its `country_colors` entry. With the `cys.1` call disabled (nothing else changed) the units showed the entry's colours. So **`restore_country_color` resets unit colours as well as the map colour**, at least for MAC.
- **UNVERIFIED:** where the restored unit colours come from (only the primary is identified, as the map colour; a save's `colors={}` block for the country would show it); whether every country is hit or only some (e.g. tags with a mod-only `country_colors` entry); whether `change_country_color = { country = X }` / `{ color = {...} }` also replaces unit colours (CYS uses `country = <overlord>` on subjects).
- **Vanilla's use** (1.37.5): `restore_country_color` only in `on_change_tag_effect` ("Clear potential messes with name / map color changes"), two Ottoman flavour events and the `restore_color_decision` (gated on `has_overriden_color_flag`, which vanilla sets wherever it calls `change_country_color = { color = ... }`). Never at startup, never on every country.
- **CYS's resets:** `cys.1` immediate (startup, `fire_only_once`; also sent from `create_subject_color_effect`'s fallback when no setting flag is set), `cys.3` immediate (decision `change_settings`, any time) and `cys.3`'s "Return Default" option, all `every_country` limited only to non-colonial; plus `on_dependency_lost` (the freed subject) and its copy of `on_change_tag_effect` (vanilla's).
- **Proposed fix (for the mod's author; not applied to the mod):** CYS only ever recolours subjects (`every_subject_country`, or the new subject in `on_dependency_gained`/`on_create_vassal`), and a freed subject is restored by `on_dependency_lost`, so the three blanket restores add `is_subject = yes` to their `limit`. Independent countries then keep their unit colours; subjects are still reset and recoloured as CYS intends. Patch: `build/macedon/cys_fix.patch` (local; `git apply` from the mod root). Open question for the author: is CYS meant to change subjects' map colour only, or unit colours too? If map only, a subject with a custom unit set may still lose its unit colours to `change_country_color` (UNVERIFIED).
- **Rule `colour_scripts`** (needs mod checks; the mod read over the game): follows `on_startup` in every `common/on_actions` file through `country_event`/`province_event` ids, on_actions `events`/`random_events` lists and scripted effects, and lists each `restore_country_color`/`change_country_color` reached with its call chain. **Warning** when one reaches every country (`every_country` without `is_subject = yes` in its `limit`) or scoped countries; **note** when it reaches subjects only (`every_subject_country`, or `every_country` limited to `is_subject = yes`). Also a note for each event, decision, on_action or scripted effect in the mod's own files that runs a colour effect inside an unrestricted `every_country` (UNVERIFIED whether a mid-game reset hits unit colours too). Limits other than `is_subject = yes` aren't evaluated.
- **Shading check (test 9 T1 after the A/B):** the "dark olive" second tunic quarter is the secondary gold. On `western_generic_01_type1` the spec-G region's diffuse is grey ~84 at spec ~0.8, so `lerp(col, col * spec.g * (210 170 40), spec.g)` gives about 61 53 25 before lighting: dark olive-brown. A brighter gold needs a lighter diffuse there (a recipe `recolour` on that region in keep mode), not different unit colours.

## 5. Composition rules (confirmed)

- **States:** `idle`, `walk`, `attack`, `retreat`. `death` and `extra_state_1–3` are commented out in every vanilla unit entity. Do not template them.
- **State → animation id → type → file.** `state = { name = "idle" animation = "idle" }` names an **id** in the entity's pdxmesh (`animation = { id = "idle" type = "rifleman_idle_animation" }`). The type resolves through `animation.asset` to an `.anim` file.
- **Western infantry pdxmesh animation ids (all 11 defined in vanilla):** `idle walk attack death retreat` (on foot), `horse_idle horse_walk horse_attack horse_death horse_retreat` (as a cavalry rider), `artillery_attack` (as artillery crew). The generator always emits all 11 for its own meshes. **Other cultures differ:** every base-game crew pdxmesh outside westerngfx (eastern, muslim, indian, asian, african, both american sets) lacks `artillery_attack`, and vanilla ships it that way. **UNVERIFIED:** how `artillery_attack` is triggered on the crew, and what a crew without it does.
- **Infantry:** root entity = infantry pdxmesh. Weapon attach node depends on the weapon: **melee on `Right_hand_node`** (halberd), **muskets on `Left_hand_node`**.
- **Cavalry:** root entity = **horse** pdxmesh (`cavalry_horse` for tiers 1–2, `cavalry_horse_3_mesh` for tiers 3–4 in western). Horse states use ids `horse_idle`, `horse_walk`, `horse_attack`, and `retreat` → `horse_walk`. It carries `attach = { name = "rider" Saddle_Node = "<rider entity>" }`.
  The **rider** entity uses a pdxmesh for the **same `.mesh` file as that tier's infantry**. Sometimes the rider's pdxmesh is the same one the infantry uses, and sometimes it's a separately named pdxmesh for the same file (DAN tier 2: entity `DAN_INFANTRY_2` uses pdxmesh `western_generic_02_type1`, while `DAN_CAVALRY_2_rider` uses pdxmesh `DAN_INFANTRY_2`; both point to `western_generic_02_type1.mesh`). The rider's states use the `horse_*` ids, and it attaches its weapon with `Right_hand_node` (`cavalry_saber`).
- **Artillery:** root = `artillery_base_mesh`, a placeholder plane whose only purpose is two bones, `infantry_node` and `cannon_node`. It carries `attach = { name = "gunman" infantry_node = "TAG_INFANTRY_n" cannon_node = "<gfx>_ARTILLERY_n_cannon" }`. **Artillery depends on infantry**: a bad infantry name breaks artillery too. The cannon entity (`artillery_mesh`) fires its muzzle effect from a state event on locator `cannon_muzzle`.
- **Weapon effects:** `state = { name = "attack" event = { time = 0.90 node = "muzzle" particle = "musket_muzzle" } }` on the weapon entity. `node` is a locator in the weapon's mesh (`muzzle`, `trigger`).
- **Skeletons** (bone names in `base_models.json`):
  - western infantry: 28 bones, the same in all 6 western/DAN infantry mesh files (8 pdxmesh names). Attach bones `Right_hand_node`, `Left_hand_node`, plus unused `attach_back`, `attach_free`. Locators include `L/R_attach_hand_ctrl`.
  - horse: 30 bones, the same in both horse meshes. Attach bone `Saddle_Node`.
  - artillery base: `root`, `infantry_node`, `cannon_node`.
  - cannon: `Root`, `Cannon`, `wheels`; locator `cannon_muzzle`.
  - Bone **parenting** (hierarchy) is deferred to Phase 3 (Blender import via io_pdx_mesh).

## 6. error.log signatures (validator must pre-empt)

Log path: `Documents/Paradox Interactive/Europa Universalis IV/logs/error.log`

| Log line | Meaning | Validator rule |
|---|---|---|
| `Failed to find entity "X" for attachment in gunman` | Artillery crew/attach target missing | Every attach target resolves |
| `Failed to find entity "..." for attachment` | Weapon/rider entity missing (often absent DLC asset) | Same; flag DLC-only targets |
| `Set a higher version on entity X` | Duplicate name, version collision | Scan vanilla + DLC + mod for name clashes |
| `Couldn't find parent clone entity X, in file "...", near line N` | Clone parent not loaded yet (defined in a later-sorting file, later in the same file, or nowhere). The unit falls back to the country's graphical-culture model | `clone_order`: parent defined earlier in load order (§3) |
| `Could not find mesh file gfx/models/...mesh` | pdxmesh `file =` wrong | Every pdxmesh file exists (mod, vanilla or DLC) |
| Black/untextured model in-game | Textures in .mesh missing or wrong format | Mesh texture refs resolve in the mesh's folder; DDS format matches base |
| `gfx/models/Units/gfx/models/...dds` not found; unit renders black | meshsettings texture name is a path; the engine prefixes the mesh folder | `texture_paths`: bare names, DDS in the mesh folder, no vanilla/DLC name; `mesh_settings`: shape, shader, textures resolve; `dds_format`: base-game base, header matches |
| (no log; frozen/T-posed unit) | State names an animation id the pdxmesh lacks | Every state animation id exists in the resolved pdxmesh; every type exists; rider pdxmesh has `horse_*`; crew pdxmesh has `artillery_attack` unless vanilla already uses that pdxmesh as a crew |

## 7. Templates

`hr_` and `MAC` are placeholders; the prefix and tag are configurable. Generated entities always carry the project `version`.

### 7.0 Phase 1 form (no new meshes)
Phase 1 entities point at **vanilla pdxmeshes** by name and define no pdxmesh or animation blocks. Every entity is a full definition, with no `clone =` (§3: clones of vanilla entities fail from a mod file that sorts first). A TAG infantry entity looks like vanilla `DAN_INFANTRY_2`:
```
# gfx/entities/hr_mac_units.asset
entity = {
    name = "MAC_INFANTRY_2"
    pdxmesh = "western_generic_02_type1"
    version = 20
    state = { name = "idle"    animation = "idle" }
    state = { name = "walk"    animation = "walk" }
    state = { name = "attack"  animation = "attack" }
    state = { name = "retreat" animation = "retreat" }
    attach = { Left_hand_node = "western_musket" }
}
```
Cavalry and artillery use the full forms in 7.2 and 7.3.

### 7.1 Infantry with its own mesh (Phase 2+)
```
# interface/assets/hr_mac.gfx
objectTypes = {
    pdxmesh = {
        name = "hr_mac_infantry_1_mesh"
        file = "gfx/models/units/hr_mac/hr_mac_infantry_1.mesh"

        animation = { id = "idle"             type = "polearm_twohanded_idle_animation" }
        animation = { id = "walk"             type = "polearm_twohanded_moving_animation" }
        animation = { id = "attack"           type = "polearm_twohanded_attack_animation" }
        animation = { id = "death"            type = "polearm_twohanded_death_animation" }
        animation = { id = "retreat"          type = "polearm_twohanded_retreat_animation" }

        animation = { id = "horse_idle"       type = "cavalry_rider_idle_animation" }
        animation = { id = "horse_walk"       type = "cavalry_rider_moving_animation" }
        animation = { id = "horse_attack"     type = "cavalry_rider_attack_animation" }
        animation = { id = "horse_death"      type = "cavalry_rider_death_animation" }
        animation = { id = "horse_retreat"    type = "cavalry_rider_retreat_animation" }

        animation = { id = "artillery_attack" type = "polearm_twohanded_attack_animation" }

        scale = 0.5
    }

    pdxmesh = {
        name = "hr_sarissa_mesh"
        file = "gfx/models/units/hr_mac/hr_sarissa.mesh"
        scale = 0.5
    }
}
```
```
# gfx/entities/hr_mac_units.asset
entity = {
    name = "hr_sarissa_entity"
    pdxmesh = "hr_sarissa_mesh"
```

### 7.7 Unit sets
A unit set has a name (`--set`, default: the tag in lowercase). The set name, not the tag, names the TAG sprite pack (`hr_<set>_units`), its entity, pack, order and localisation files, and the unit keys (`hr_<set>_infantry_1`). Entity names stay `TAG_INFANTRY_n` (engine pattern). Set names are lowercase and can't end in `gfx`, which keeps them apart from graphical-culture files.

**Culture triggers** (2026-10-15): a set targets tags, primary cultures, or both (`Nation.cultures`; CLI `--culture`, GUI "Culture(s)"). Its one pack's trigger is `tag = MAC`, `primary_culture = macedonian` or `OR = { tag = MAC primary_culture = macedonian }` (vanilla's culture packs use `primary_culture`, e.g. `dlc003_pol_sprite_pack`), so the look survives tag changes such as forming a new nation. A set with no tag needs a set name; its entities are named after the prefixed set (`hr_macedonian_INFANTRY_1`, `Naming.entity_owner`; names pick nothing in game, the pack does). Unit colours stay per tag: countries matched by culture keep their own `country_colors` entries. Rules: `sprite_packs` (the trigger), `cultures` (each culture is in `common/cultures`, vanilla or, with mod checks, the mod; warning without mod checks, error with), `pack_order` (packs at an equal or higher order that match, or may match, a country of one of the cultures: `trigger_matches` with an unknown tag; unowned DLC packs never load). INTEGRATION.md states the trigger. UNVERIFIED: whether pack triggers are re-checked during play (a culture change or tag switch mid-game).

### 7.8 Procedural parts (Phase 3)
A loadout (`core/loadout.py`) dresses the TAG set; the gfx-culture defaults stay undressed. Each part is a static mesh made from scratch, in the set's own folder with its textures beside it (bare names resolve there), a pdxmesh with no animations and an entity with no states:
```

pdxmesh = {                                   # stance: the vanilla body with another animation set
    name = "hr_mac_infantry_1_mesh"  file = "gfx/models/Units/western_generic_01_type1.mesh"
    animation = { id = "idle"   type = "spear_shield_idle_animation" }
    animation = { id = "walk"   type = "spear_shield_moving_animation" }
    animation = { id = "attack" type = "spear_shield_attack_animation" }
    ... every other id of the base pdxmesh, unchanged ...
    scale = 0.5 }
# gfx/entities/hr_mac_units.asset
entity = { name = "hr_mac_hoplon_1"  pdxmesh = "hr_mac_hoplon_1_mesh"  version = 20 }
entity = { name = "MAC_INFANTRY_1"  pdxmesh = "hr_mac_infantry_1_mesh"  version = 20  state = { ... }
    attach = { Right_hand_node = "hr_mac_dory_1" Left_hand_node = "hr_mac_hoplon_1" head = "hr_mac_crest_1" } }
entity = { name = "MAC_ARTILLERY_1_crew" ... }   # only when the crew is dressed apart; the gunman's infantry_node points at it
```
Names (`naming.py`): parts `hr_<set>_<kind>_<tier>` for the infantry, `hr_<set>_<kind>_<role>_<tier>` for the rider and crew (the role before the tier: names ending `_rider`/`_crew`/`_cannon` are the unit entities'); crew entity `TAG_ARTILLERY_n_crew`; stance pdxmeshes `hr_<set>_infantry_n_mesh` (the retextured one if there is one) and `hr_<set>_crew_n_mesh`. Identical parts at one tier are built once and shared between roles.

### 7.9 Special units (research, 2026-10-15, 1.37.5) — not used
**Conclusion: mods can't add special unit types, and special units have no model hooks. Unit looks come from sprite packs only** (`sprite_infantry`, `sprite_cavalry`, `sprite_artillery`, chosen by the country's pack and sprite level). The generator doesn't touch special units; a total conversion may rename and re-gate them by hand.
- **Fixed list.** Land (15): janissaries, banners, cawa, carolean, hussars, tercio, musketeers, samurai, qizilbash, mamluks, streltsy, cossacks, rajputs, marines, revolutionary guard. Naval (6): geobukseon, man_of_war, galleon, galleass, caravel, voc_indiamen. No definition folder in `common/`; each type has its own hard-wired defines (`common/defines.lua` ~1254-1560: `<TYPE>_BASE_COST_MODIFIER`, `_MANPOWER_COST_MODIFIER`, `_STARTING_STRENGTH`/`_MORALE`, `_USES_CONSTRUCTION`, `*_MAXIMUM_RATIO`, `CREATE_JANISSARIES/CAWA/HUSSARS_MIL_COST`, `CORRUPTION_FROM_BANNERS`), its own modifier names and its own unit-panel band sprites (`interface/unitpanel.gfx`).
- **No model hooks.** Across base game and every DLC, sprite packs use only the three keys above. The only special-unit-named entities, Winged Hussars' `POL/LIT/RUS_CAVALRY_n_hussar`, sit in the ordinary `sprite_cavalry` slot of culture packs (`dlc003_*_sprite_pack`, `primary_culture = polish/lithuanian/russian`, order 70): they re-skin all cavalry of those cultures, not the hussar unit. A special regiment shows the country's infantry/cavalry entity for its tier.
- **Moddable per type:** name (localisation: `janissary_regiment`, `STRELTSY_REGIMENT`, `STRELTSY_NAME`, ...); combat bonuses (`<type>_regiment` / `<type>_ship` static modifiers in `common/static_modifiers/00_static_modifiers.txt`, a single file: override it whole); cost, starting strength/morale, construction and caps (defines); who may recruit and how many (`allowed_<type>_fraction`, `amount_of_<type>`, `allow_banners`/`allow_cawa`, `can_recruit_hussars/cossacks/rajputs/revolutionary_guards`, `enables_estate_janissaries`), granted through government reforms, estate privileges, ideas, ages, policies and event modifiers.
- **Fixed:** the list of types, each type's base category (infantry/cavalry; UNVERIFIED for banners and rajputs, not stated in any file), the province raise flow of janissaries, banners and cawa (`provinceview.gui` state views; how many can be raised is engine logic), pips/speed/model (the country's current infantry/cavalry unit and sprite pack).
- **One tag, one tier, one cavalry look.** Each pack has one cavalry entity per tier; the map shows one model per army by its dominant type, chosen by sprite level (in-game test 1). Two cavalry unit types of one tag at one tier can't look different. The only lever is country-wide: another pack's trigger swaps all of a tag's cavalry (UNVERIFIED whether pack triggers are re-checked during play).
- Repurposing ideas for a Hellenistic mod, if wanted later: Companions = hussars (`cavalry_shock` +1, morale damage +50%, no estate); pike phalanx = tercio (shock damage received -30%); hypaspists = carolean or samurai; light cavalry = cossacks/mamluks; peltasts = cawa; archers/slingers = streltsy or musketeers; epibatai = marines; polyremes = galleass/geobukseon. Banners suit Companions poorly (start at 10% strength, add corruption, raised per province).

### library/scanner.py
- Reads the base game and `dlc/*/*.zip` in place (stdlib `zipfile`). Path lookups ignore case, because scripts write `Units` and `units` interchangeably and Linux is case-sensitive.
- Indexes entities (`gfx/entities`), pdxmeshes (`interface/**/*.gfx` → `objectTypes`), animation types (`gfx/models/**/*.asset`), sprite packs, pack order, the graphical-culture list, `mil.txt` sprite levels and the game version. Every definition records its source file and DLC, so later validator rules can detect version collisions.
- Parses binary `.mesh` files (shader, texture names, bone names, locators with parent bone) and DDS headers.
- Script text is read with `pdxscript.parser` (lossless; round-trips all 8,852 vanilla + DLC script files byte-for-byte). Two DLC116 files are malformed in vanilla: `116_sprites.txt` ends inside an unclosed block and `scanup_NOR.gfx` has a stray `}`. The parser reads every pack and pdxmesh in both and reports the problem as a warning.
- CLI: `python -m eu4unitgen.library.scanner --eu4 "<install>" [--tag DAN] [--gfx westerngfx] [--no-dlc] [--out ...]`, or set `EU4_PATH`.
- Files in the `dlc/` folder don't prove the user owns that DLC (Steam installs them all), so DLC ownership is a project setting.

### base_models.json (schema_version 2)
Metadata only: names, paths, bone names, header facts. No game files or script text.
- `reference_nation`: the base-game chain for one tag (default DAN): sprite pack, per-tier composition, and `dlc_overrides` (DLC packs listing that tag's entities, their order, triggers, partial tiers, and redefined entities with versions).
- `graphical_culture_defaults`: the same for the gfx culture's pack.
- `recolour_bases`: per tier, the generic gfx-culture pdxmesh for infantry, horse, rider and cannon, each with `uses_country_colour`. This is the default base for recolour and kitbash.
- `pdxmeshes`: file, scale, `shader`, `uses_country_colour`, texture names + dir, skeleton id, locators, animation id → type map.
- `skeletons`, `animation_types` (with `file_exists`), `entities` (raw fields, including clone), `textures` (DDS headers), `sprite_levels`, `graphical_cultures`, `game_version`.

### Stack decisions
- **Python + PySide6**: same language as bpy/io_pdx_mesh, cross-platform Qt, LGPL.
- **Pillow ≥ 11.2.1** writes DXT1/DXT3/DXT5/BC2/BC3/BC5 via `im.save("x.dds", pixel_format="DXT5")`.
- **texconv** (optional, Windows): `texconv -ft DDS -f BC3_UNORM in.png` gives better quality and a full mip chain. Linux fallback: Compressonator or ImageMagick.
- **Blender** only as a subprocess. Pinned: **Blender 4.2.23 LTS + io_pdx_mesh 0.91** (`core/project.py` `BLENDER_VERSION`, `IO_PDX_MESH_VERSION`). Default path `C:\Program Files\Blender Foundation\Blender 4.2\blender.exe` on Windows, `blender` on PATH on Linux, overridable with `$BLENDER_PATH` or the GUI Settings screen. Verified on the user's machine (2026-10-14): a vanilla eastern infantry mesh imports with its skeleton. Known addon issues: animation export errors, custom normals ignored on re-export, `No module named 'imp'` on newer Blender.
- **3D preview**: Blender-rendered thumbnails (no custom renderer in MVP).
- **License**: GPL-3.0.

### Mesh approaches (ranked)
1. Entity copy / re-point onto vanilla pdxmeshes (no mesh work). Covers all 12 slots immediately.
2. Texture swap/recolour on a copy of a base mesh (default base: `recolour_bases`), re-exported to point at new DDS files.
3. Kitbash in headless Blender: attach pre-weighted accessories (helmets, shields) to vanilla skeleton bones, then export.
4. Procedural variants on the same armature (needs human QC).
5. New rigged models: out of scope.

Edited meshes keep the vanilla skeleton, so they **reuse vanilla animation types**. io_pdx_mesh preserves armature structure on import/export.

## 9. Legal constraints

- Paradox EULA: mods may be made and shared; you may not distribute the game with the mod, nor charge or take donations for mods.
- DLC assets: only usable if steps are taken so only DLC owners can use them. **Never bundle DLC assets.** Read them from the user's install and gate with `has_dlc` where possible. Never use a DLC mesh as a recolour/kitbash base.
- Prefer references to vanilla names and paths over copying base-game files. Generated entities restate a vanilla entity's fields (names of pdxmeshes, animations, attach targets), which copies no Paradox asset; `clone =` can't be used on vanilla parents from a mod file that sorts first (§3).
- Not legal advice. Paradox can remove mods at its discretion.

- Weighting variants (each part, all on the unmodified 28-bone skeleton):
  - **A auto:** Blender automatic (heat) weights, limited to plausible bones (tail: hip, lower_spine, mid_spine, L/R_thigh; ponytail: head, top_spine, mid_spine, shoulders), then cut to the 4 largest and normalised;
  - **B rigid:** tail 100% hip; ponytail 100% head;
  - **C gradient:** tail hip → lower_spine along the length (root 100% hip, tip 50/50); ponytail head → top_spine (root 100% head, tip 30/70).
- Animations: each of idle, moving, attack, every frame.
- Renders (Eevee, orthographic, neutral grey materials, body semi-dark, additions coloured):
  - front, side, rear at 8 evenly spaced frames per animation, plus the frame with the worst metric;
  - one contact sheet per variant × animation;
  - a "map-scale" render (the unit ~48 px tall) per variant.
- Metrics per frame (JSON):
  - **stretch:** edge length / rest length (min, max, 95th percentile);
  - **penetration:** addition vertices inside the body mesh (ray-parity test) and the deepest one (units);
  - **flips:** triangles whose normal turns > 90° from rest, relative to the driving bone;
  - **root drift:** root-ring vertices' distance from rest in the hip/head frame;
  - **tail-through-legs:** the tail's lowest point vs the thighs' rear surface;
  - **ponytail-through-back:** penetration into the torso.
- **Pass criteria** (per part and variant, in all three animations):
  1. stretch within 0.85-1.20 for every edge, and 95th percentile within 0.92-1.08;
  2. penetration: idle and moving 0 vertices deeper than 0.10 units (~1.2 cm); attack ≤ 3% of vertices, none deeper than 0.30;
  3. no flipped triangles;
  4. root drift ≤ 0.05 units;
  5. tail never passes in front of the thigh plane; ponytail never enters the torso by more than criterion 2 allows;
  6. **user sign-off** on the contact sheets and map-scale renders (reads as a tail/ponytail, no visible popping or twisting).
- **Outcome:**
  - The technique is **acceptable without modifying the skeleton** if at least one variant per part passes 1-6. Automatic weights (A) are reported on their own: passing with B/C only means "authored weights, not auto".
  - If no variant passes: report which criterion fails where, and estimate the alternatives (rigid fallback, shorter geometry, new bones + animations).

**Required pipeline component: procedural chain-weight tool** (automatic heat weights are rejected; R0, R0b). It sets skinned weights from the part's geometry and a declared bone chain:
- **(a) along-length gradient** for parts that grow away from the chain (tail: root 100% first bone, tip blended; R0 C passes);
- **(b) chain projection** for parts lying along the chain, **never blending across a high-rotation joint** (`head`/`top_spine`; R0b E fails). A span that crosses one is split or kept rigid on one side.

Common to both modes:
- ≤4 influences per vertex, normalised;
- skeleton bones only;
- root rings locked 100% to the root bone.

A validator rule checks the result: influences, sums, bone names, and that no weight sits on a bone outside the declared chain.

### Track F: Prompt front end (PLANNED 2026-10-17; mockups approved with changes)

The app opens on a prompt screen like the AI app builders (one box, example chips, one Generate button). Everything built so far stays, unchanged, behind an "Advanced editor" link; both edit the same character spec, so they stay in sync and share undo.

**Screens**

#### M4. Stages
Applies to every stage:
- **Reproducible from configs:** every stage reruns from configs and earlier stages' outputs, with no manual mesh editing. Each writes a versioned folder (`<subject>/master/vNNN/…`, content-hashed, read-only once written) and a provenance log (generator, parameters, seeds, input hashes).
- **Proof package, required to pass:** the artifact; a render; a comparison with the reference; the metrics; a list of visible discrepancies; evidence the geometry is new (generator provenance, plus `vanilla_distance` for the body).

**S1. Reference analysis**
- **In:** the original sheet, the subject config.
- **Tools:** BiRefNet; SDXL inpainting; the annotation screen (new, PySide6).
- **Operations:**
  1. Crop the views.
  2. Make masks.
  3. Inpaint the rider, shield, lance and reins: masks from boxes plus BiRefNet's rider/horse split, then 4 seeds each.
  4. Region labels and landmarks per view.
  5. List the conflicts between views.
- **Out:** `refs/original/` (untouched), `refs/clean/vNNN/` (with the inpaint masks), labels, landmarks, a conflict list, a palette per region.
- **Validation:** the inpainted area per view (share of the horse mask). Inpaint candidates are scored for continuity (seam colour and edge difference) and ranked by it.
- **Fail:** the inpaint invents structure (a new strap, a leg); labels or landmarks missing.
- **Recovery:** other seeds; a smaller mask; mark the area "unknown" instead of inpainting it.
- **Proceed:** human checkpoint **H1**.

**S2. Master body (horse anatomy)**
- **In:** S1; the anatomy template (horse); TripoSG candidates (N seeds on the cleaned view L).
- **Operations:**
  1. Fit the camera and pose per view (S3's solver).
  2. Optimise the anatomy parameters (≈40) to the outlines (labels: coat, legs) and landmarks in both views.
  3. Use TripoSG's shell only as a depth prior: chest and barrel widths, which no 2D view fixes.
  4. Head parameters from L.
  5. Tail curves from R.
- **Out:** the body in the reference pose and in a neutral rest pose, both on the vanilla skeleton's bones (bones only), with the `evidence` attribute.
- **Validation:** silhouette IoU and landmark error on the bare-coat regions; anatomy sanity (joint angles, limb lengths within horse ranges, kept in the template, not tied to this horse).
- **Fail:** IoU or landmarks under the gates; the optimiser stuck; implausible anatomy.
- **Recovery:** restart from other initialisations; a wider parameter group (e.g. a free head shape); the best TripoSG seed as a prior.
- **Proceed:** the gates (M5).

**S3. Reference-camera reconstruction** (a solver used by S2 and every later stage)
- **Solves per view:** focal length, camera rotation and translation, joint angles of the pose.
- **Method:** scipy (Nelder-Mead / Powell; CMA-ES if approved) on silhouette distance plus landmark error, with Blender Workbench silhouette renders. Each evaluation is a fast flat render or our own numpy raster of a decimated proxy.
- **Out:** a camera per view, the reference pose, residuals.
- **Fail:** residuals over gate.
- **Recovery:** more landmarks (back to H1); fit the two views independently.

**S4. Armour (Geometry Nodes plates)**
- **In:** the body.
- **Shell:** offset by the armour thickness and fitted to the armour outline in L and R (the same optimiser, on offset parameters per region).
- **Coverage:** from the region labels projected onto the surface through each solved camera, with symmetry for the unseen side.
- **Plates:** Poisson-distributed points on the shell, each oriented along a per-region direction field (rows run around the neck, down the chest). Overlap comes from ordering and tilt.
- **Configurable per region:** plate shape (a small curved mesh with real thickness), size, spacing, tilt and curvature.
- **Out:** the live Geometry Nodes setup plus a realised cache.
- **Validation:**
  - plate count and spacing against the reference's plate frequency (FFT of the region's pixels at the solved camera vs the render);
  - coverage IoU per region;
  - penetrations (plates through the body or each other; counted by BVH);
  - gaps (body visible through the plates).
- **Fail:** penetrations or gaps over threshold; frequency off by > 15%.
- **Recovery:** optimise offset and tilt; regional plate size; a smoothed shell at high curvature.

**S5. Caparison (cloth simulation)**
- **In:** body and armour (a smoothed collision proxy, not the plates), the panel pattern from the labels (cut lines, hem heights per view).
- **Operations:**
  1. Panels as flat patterns pinned along the top seam.
  2. Simulate in background Blender with fixed settings and seed.
  3. Freeze the result into the master as a new version; the pattern and settings stay as the procedural source.
- **Validation:** silhouette and hem line against L and R; intersections with the body or armour; stretch (cloth edge length vs pattern); comparison with TripoSG's drapery shell.
- **Fail:** explosion, intersections, panels sticking, the hem off the reference.
- **Recovery:** a grid of a few stiffness, collision-distance and pin sets as candidates, best by metrics; then pattern edits (hem length, panel width), optimised.

**S6. Decorative geometry and chanfron**
- **Chanfron:** a surface patch over the fitted head (forehead, nose, cheek plates), eye openings at the eye landmarks, an offset, thickness, and a ridge.
- **Trim, borders, fringe:** curves along the cloth panels' boundaries after S5.
- **Straps:** curves projected on the surface between landmarks (breast strap, bridle, girth); buckles and rosettes as instanced small meshes from a parts library (our own, made from scratch).
- **Tassels:** instanced along hem curves.
- **Validation:** the key-detail checklist (M5 metric 6); clearance (no detail inside the body).
- **Fail:** a detail missing or misplaced against its landmark.
- **Recovery:** re-place by landmark; add the generator instance named in the detail list.

**S7. Texturing** (materials)
- **Procedural base:** metal plates, cloth, gold, leather and coat, with colours fitted to the observed region palette in Lab (lighting-compensated, see M5).
- **Unique ornament** (crosses, embroidered borders): projected from the cleaned views through the solved cameras where `observed`; mirrored for `symmetry`; generated (ControlNet depth + IP-Adapter, if approved) or a procedural decal for `prior`, and flagged.
- **De-lighting** of projected pixels: divide by the shading of our own render of the fitted geometry under an estimated light. The illustration's painted light can't be removed fully; the residual is reported.
- **Out:** PBR master maps (base colour, metallic, roughness, normal).

**S8. Evaluation, correction, approval**
- **Evaluate:** all metrics (M5) in both reference cameras.
- **Correct:** the M6 loop, up to a capped number of rounds.
- **Approve:** **H3**.
- **Then stage 7** (game model, **H4**), then stage 8 (EU4 integration, then an in-game test as before).

#### M5. Automated fidelity evaluation
- **Renders in each solved reference camera, three kinds:**
  1. **flat ID:** one colour per component and region, for masks;
  2. **albedo:** for colour;
  3. **lit:** a light fitted to the reference's dominant light direction (estimated from the shading of the observed coat and metal against our normals), for structural metrics.
- **Masks:** the horse after rider removal. Inpainted pixels are scored separately and weighted lower; they are never counted as observed truth.
- **Saved per evaluation:** side-by-sides, overlay and difference images, per-region masks, `metrics.json`.
- **Metrics, each reported on its own:**
  1. **Silhouette:** IoU per view and per region (legs, head, neck, body, cloth), plus contour distance (mean and 95th percentile, px / body length). Per-region IoU so a thin leg or a missing tail can't hide inside a good overall IoU.
  2. **Colour:** ΔE2000 between region mean colours (albedo render vs the reference's region, lighting-compensated), plus a histogram distance.
  3. **Landmarks:** projected named master landmarks vs annotated ones, px / body length, per landmark.
  4. **Armour coverage:** per-class IoU and a confusion matrix of the label map (scale, cloth, trim, chanfron, coat, strap) vs the rendered ID map.
  5. **Structure / perception:** SSIM on edge maps; LPIPS and DINOv2 similarity if approved. Secondary only: they reward texture-like noise and are fooled by style.
  6. **Key details:** a per-subject list (cross on each panel, breast strap, bridle rosette, fringe, tassels, chanfron ridge, eye openings, tail…), each with its expected place. Present = the master has the generator instance **and** its projection lands within tolerance of its reference position **and** a local patch match passes.
- **Gates (hard, before any composite):**
  - region IoU ≥ 0.85 on observed regions;
  - landmark error ≤ 2.5% of body length (each);
  - coverage class IoU ≥ 0.7;
  - every key detail present;
  - zero penetrations over 1 mm (master scale);
  - ΔE2000 ≤ 8 per region.

  All assumed: calibrated in E-D (M9). A failed gate fails the stage whatever the composite.
- **Composite** (ranking candidates only, never pass/fail): a weighted sum with documented weights, stored in the subject config. Starting proposal: silhouette 0.25, landmarks 0.20, coverage 0.20, details 0.15, colour 0.15, structure 0.05.
- **Style accounting:**
  - the reference is painted: high-frequency texture and highlights won't match a render;
  - colour is compared on region means and histograms, not per pixel;
  - structure is compared on edges, not raw pixels;
  - camera mismatch is removed by the solved camera; the residual is reported per view.

#### M6. Correction: how each failure gets fixed automatically
| Failure (found by) | Automatic fix | Kind |
|---|---|---|
| Body outline or landmark off (1, 3) | re-optimise anatomy parameters, with pose and camera fixed; then joint, camera and pose | parameter optimisation |
| Pose mismatch (3, leg landmarks) | optimise joint angles | parameter optimisation |
| TripoSG shell defects (lumps, fused parts, a wrong chest) | best of N seeds (8 seeds ≈ 25 min), ranked by the gates and composite on its depth-prior role | best of candidates |
| A bad inpaint (S1) | other seeds; a smaller mask; mark the area unknown | best of candidates / regenerate region |
| Armour coverage off (4) | re-project the labels; widen or shrink the region masks by optimisation against coverage IoU | parameter optimisation |
| Plate size or row direction off (FFT) | optimise plate size, spacing and the direction-field angle per region | parameter optimisation |
| Plate penetrations or gaps | optimise offset, tilt and scale; smooth the shell locally where curvature is high | parameter optimisation / regenerate region |
| Cloth sim failure or bad drape (1, hem landmarks) | candidates over stiffness, collision distance and pins; then optimise the pattern's hem and panel widths | best of candidates, then optimisation |
| Detail missing or misplaced (6) | re-place by landmark; add the missing instance from the detail list | rule-based regenerate |
| Region colour off (2) | solve material colours in Lab against the compensated reference colour | direct solve |
| Texture seam or inconsistency on unseen areas | regenerate that area (ControlNet + IP-Adapter if approved, else procedural), best of N by seam metric | regenerate region / best of candidates |
| Global failure after K rounds | stop and report; never lower a gate without the user's OK | human |

Every correction round is a new master version; the loop keeps the best version and the history.

#### M7. Automation vs judgement
- **Fully automatable, and achievable:** every stage's execution, the metrics, the gates, the candidate generation and ranking, versioning, the proof packages, the evidence maps, deriving the game model.
- **Hard to automate (artistic judgement):**
  - whether folds look like cloth;
  - whether a guessed right side is plausible;
  - which view wins when the two illustrations disagree;
  - how much of the illustration's stylisation to copy;
  - whether a high-scoring master actually *looks like* the reference;
  - what to give up for the game model.
- **Human checkpoints:**
  - **H1, after S1 (~10-15 min):** approve the cleaned references (the inpaint is plausible, nothing invented), the region labels, the landmarks, and the conflict choices per detail.
  - **H2, after S2 (~5 min):** approve the anatomy and pose (side-by-sides plus the evidence map), before armour and cloth are built on it.
  - **H3, after S8 (the main approval):** the master against the reference with the full metric report and discrepancy list. Approve, or name what's wrong (which becomes a new gate or detail).
  - **H4, after stage 7:** the game model vs the master at GAME_CLOSE and map scale; approve the losses.
  - **In-game test:** as before (checklists).

Between checkpoints nothing waits for the user.

Automatic mask generation: a 64×64 point grid, pred IoU ≥ 0.5, stability ≥ 0.7 (stricter defaults left L's neck unsegmented); fp32, because fp16 breaks the NMS post-process; transformers' multi-crop mode is broken (a tensor size error), so single crop. About 30 s for both views, 3.4 GB VRAM.
  - **Segment vote:** inside each segment, ambiguous pixels (leather or unmatched) take the majority class of the segment's confident pixels when those are at least 30% of it; a mostly-leather segment (a strap) keeps its colours. Coat abstains (keeps its zone pixels, never votes or spreads): in v005 a segment joining the tail and haunch voted the haunch into coat. A `saddle` zone in L turns scale into leather (seed 88's grey-leather saddle reads as metal by colour).
  - v006 (approved at H1): L scale 25%, cloth 28%, trim 16%, leather 12%, chanfron 9%, leg 9%; R cloth 24%, tail 23%, scale 21%, trim 18%, leather 6%, leg 9%; unclassified 0 on both. By segment vote: 27% (L) and 11% (R); by neighbour: 15% and 10%. Left: a few leather specks in L's shaded lower caparison; the saddle zone's straight edge (on inpainted pixels).
