# eu4unitgen — Technical Specification

Target: EU4 1.37.5 (verified against `release_1.37.5`, rev `835bfdf8`). Scope now: **land units only** (infantry, cavalry, artillery, 4 sprite tiers each). Later: ships, generals/advisor portraits, city models.

Items marked **UNVERIFIED** are not yet confirmed against the user's install or in game. Phase 0 confirmed everything not marked. The machine-readable record of the vanilla chain is `src/eu4unitgen/library/base_models.json`, generated by `library/scanner.py`.

---

## 1. Goal

For a given nation (tag) and graphical culture, the app generates every file EU4 needs to show that nation's land units on the map, validates the whole dependency chain, and exports into a mod folder. It works on two levels:

- **Script level (deterministic):** entities, pdxmesh definitions, sprite packs, pack order, unit definitions, tech unlocks, localisation, country/culture wiring.
- **Asset level:** textures (recolour, pattern overlay, spec masks) and meshes (retexture, kitbash onto vanilla skeletons via headless Blender). New rigged models from scratch are out of scope.

---

## 2. The EU4 land-unit file chain

Every map unit is an **entity**. The entity points to a **pdxmesh** (a named model). The pdxmesh points to a **.mesh** file, which names its **textures**. The pdxmesh also maps **animation ids** to **animation types**, and each type points to an `.anim` file. Entity states pick an animation id. Entities list **attachments** (weapons, riders on horses, gun crews). A **sprite pack** tells the game which entities a country uses at each of the 4 tech tiers.

| Layer | Location (vanilla) | Purpose | Links to |
|---|---|---|---|
| Mesh | `gfx/models/Units/*.mesh` | Geometry, skeleton, material (shader + texture names), locators | DDS files |
| Textures | same folder as the mesh | Colour, normal, specular + country-colour mask | — |
| Animation clips | `gfx/models/Units/animation/*.anim` | Skeletal clips | Skeleton in mesh |
| Animation types | `gfx/models/Units/animation/animation.asset`: `animation = { name = "<type>" file = "<x>.anim" }` | Script name for a clip. `file` is relative to the `.asset`'s folder | `.anim` |
| pdxmesh | `interface/assets/*.gfx`, inside a top-level `objectTypes = { ... }` | Script name for a mesh + `animation = { id = ... type = ... }` map + `scale` | `.mesh`, animation types |
| Entities | `gfx/entities/*.asset` | `TAG_INFANTRY_1` etc.: pdxmesh + states + attachments | pdxmesh, other entities |
| Sprite packs | `gfx/sprite_packs/*.txt` | Which entities a tag or graphical culture uses per tier | Entities |
| Pack order | `gfx/sprite_packs_order/*.txt` | `pack_name = number` | Sprite packs |
| Graphical culture | `common/graphicalculturetype.txt`; country file `graphical_culture = xxxgfx` | Default unit/portrait/city set | gfx sprite pack + default entities |
| Unit stats | `common/units/*.txt` | type, unit_type (tech group), maneuver, pips | Tech + loc |
| Tech unlock | `common/technologies/mil.txt` | `enable = <unit>`, `sprite_level` | Units |
| Localisation | `localisation/*_l_english.yml` | `<unit>:` and `<unit>DESCR:` | Units |

Base game and DLC both put pdxmeshes in `interface/assets/*.gfx`; DLC116 ships `interface/assets/scanup_DAN.gfx` next to `gfx/entities/scanup_DAN_units.asset`. No vanilla or DLC file defines a pdxmesh inside `gfx/entities`.

**Project file layout (follows vanilla):**
- `interface/assets/<prefix>_<tag>.gfx`: pdxmeshes in `objectTypes = { }`
- `gfx/entities/<prefix>_<tag>_units.asset`: entities
- `gfx/models/units/<prefix>_<tag>/`: meshes and textures (Phase 2+)
- `gfx/models/units/<prefix>_<tag>/<prefix>_animations.asset`: animation types, only for new `.anim` clips. Vanilla has `.asset` animation files in several `gfx/models/` subfolders (`Units/animation`, `ships`, `Mapitems`, `animated_mapobjects`). **UNVERIFIED:** that the engine loads a mod-added animation `.asset` from a new subfolder. Reuse vanilla animation types whenever the vanilla skeleton is kept.

Entity names and pdxmesh names are **separate namespaces**. Vanilla has an entity `DAN_INFANTRY_2` and a different pdxmesh also named `DAN_INFANTRY_2`. `naming.py` still gives generated pdxmeshes a `_mesh` suffix so the two can't be confused.

### Sprite levels (vanilla, confirmed)
| Tier | sprite_level | Vanilla MIL tech | Year |
|---|---|---|---|
| 1 | 1 | 0 | 1350 |
| 2 | 2 | 12 | 1557 |
| 3 | 3 | 21 | 1674 |
| 4 | 4 | 26 | 1745 |

Level 5 (MIL 30, 1805) is commented out in `mil.txt`. A total conversion controls `mil.txt` and can remap tiers to its own eras, but there are still only 4 land tiers.

The game shows **one model per army**, chosen by the dominant unit type, so every nation needs all 3 types × 4 tiers = **12 root entities**, plus attachment entities.

## 3. Naming, versions, sprite packs

- Tag entities: `TAG_INFANTRY_1..4`, `TAG_CAVALRY_1..4`, `TAG_ARTILLERY_1..4`; riders `TAG_CAVALRY_n_rider`.
- Graphical-culture defaults: `<gfx>_INFANTRY_n`, `<gfx>_CAVALRY_n`, `<gfx>_CAVALRY_n_rider`, `<gfx>_ARTILLERY_n`; cannons `<gfx>_ARTILLERY_n_cannon`. Western artillery tiers 2–4 clone `westerngfx_ARTILLERY_1` as `westerngfx_ARTILLERY_n_generic`.
- DLC variants carry suffixes (e.g. `_evup`, `_generic`).
- Cloning: `entity = { clone = "SRC" name = "NEW" ... }`. Fields given on the clone override the source (e.g. `pdxmesh`). DLC116 combines `clone` and `version` in one entity.
  **UNVERIFIED:** whether a clone's `attach` blocks replace the source's by attach `name` or are added. Vanilla always restates the named attach (`name = "rider"`, `name = "gunman"`) on clones, and the generator does the same.

### version
- Vanilla base-game entities have **no** `version` line.
- DLC116 redefines `DAN_INFANTRY_1`, `DAN_CAVALRY_1`, etc. with `version = 4` to replace the base-game definitions. `weapons.asset` uses `version = -1` on an entity it deliberately duplicates.
- The project uses a project-wide `version` (default 20) on every generated entity. Collisions log `Set a higher version on entity X`.
- **UNVERIFIED:** that a missing version counts as 0, and which definition wins on a tie.

### Sprite packs
- **Since 1.30, sprite packs assign entities to tags** via `country_trigger`. Indices `0–3` = tiers 1–4.
- **Partial packs are confirmed:** `dlc116_DAN_sprite_pack` lists indices 0, 2, 3 only.
- **Graphical-culture packs.** Vanilla wires each culture's defaults through a pack in `gfx/sprite_packs/+00_base_sprites.txt`:
  ```
  westerngfx_sprite_pack = {
      country_trigger = { always = no }
      graphical_cultures = { westerngfx }
      sprite_infantry = { 0 = westerngfx_INFANTRY_1 ... }
      ...
  }
  ```
  **A new graphical culture needs its own default `<gfx>_INFANTRY/CAVALRY/ARTILLERY_1–4` entities plus a gfx sprite pack like this one**, or countries without a tag pack have no models. The generator always emits a TAG set, a gfx-culture default set and both packs.
- **Pack order.** Base-game packs (including `dan_base_sprite_pack` and all gfx packs) have **no** entry in `sprite_packs_order`. The vanilla order file says the default is 0 and *"anything higher will take priority"*. Its bands are 0 gfx culture, 10 culture groups, 20 culture group, 30 primary cultures, 40 primary culture, 50 tags, 60 tag, 70 more specific. DLC goes up to 100 (`dlc116_DAN_sprite_pack = 100`).
  - The generator writes an order entry for every **tag** pack. The default is 110 (configurable), so a tag pack beats any vanilla or DLC pack whose trigger might also match a total-conversion nation. The validator warns when a vanilla or DLC pack with a higher number could match the same country.
  - gfx-culture packs get no order entry, matching vanilla.
  - **UNVERIFIED (Phase 1 in-game test):** that a higher number wins, which is Paradox's comment and has not been tested.
- **UNVERIFIED (Phase 1 in-game test):** the engine's fallback order (tag sprite pack → TAG entity names → gfx culture pack/entities).

### Graphical culture list
`common/graphicalculturetype.txt` is a bare list of names, one per line, with no braces or keys (e.g. `westerngfx`). It is a single file, not a folder. At export the generator writes it into the mod by reading the user's vanilla list and adding the new names. It is never stored in the repo.
**UNVERIFIED:** that the mod's copy replaces the vanilla file (expected Clausewitz behaviour for a single file) rather than merging with it.

## 4. Shaders, textures, country colours

Shaders (code in `gfx/FX/pdxmesh.lua`):

| Shader | Use |
|---|---|
| `PdxMeshColor` | Most generic units. **Spec map RGB = country primary/secondary/tertiary colour masks.** |
| `PdxMeshStandard` | Fixed-colour meshes: weapons, cannons, the artillery base, and some nation-specific uniforms (`DAN_01.mesh`, `DAN_04.mesh`) |
| `PdxMeshTextureAtlas` | Prints country flag, UV range 0.05–0.95 |
| `PdxMeshSnow`, `PdxMeshAlphaBlend`, `PdxMeshAlphaBlendNoZWrite`, `PdxMesh_NoFoW_NoTI`, `Collision` | Special cases |

**Nation-specific meshes may not take country colours.** DAN's tier 1 and 4 uniforms use `PdxMeshStandard`; the generic western meshes (`western_generic_01–04_type1`, `cavalry_horse`, `cavalry_horse_03`) use `PdxMeshColor`. `base_models.json` records `shader` and `uses_country_colour` for every pdxmesh. **Recolour and kitbash bases default to the graphical culture's generic meshes** (`recolour_bases` in `base_models.json`), not to nation-specific ones. Cannons are `PdxMeshStandard` and never take country colours.

### Texture facts (confirmed, western chain)
- Texture names inside the `.mesh` material are **bare file names**, resolved in the mesh's own folder.
- Formats: **diffuse DXT1, normal DXT1, specular DXT5**. Full mip chain; no DX10 header. Infantry textures and horse normal/spec maps are 512×512. Horse diffuse maps and all three cannon maps are 256×256. The weapon sheet is 512×256. The artillery base uses 4×4 `nospec.dds`/`nonormal.dds` placeholders.
- Default DDS output: copy the base texture's format and size (read from `base_models.json`/the header). That means BC1/DXT1 for diffuse and normal and BC3/DXT5 for spec, **not sRGB**, no DX10 header, full mip chain.
- Spec map **alpha = gloss**. Existing spec maps contain zero-alpha areas that still hold colour, so don't treat alpha 0 as empty.
- Gloss presets from community trial and error: ~1–4% matte, 5–10% cloth, 10–16% metal, 17–20% mirror; above that, extreme shine. UI presets: 3%, 8%, 13%.
- Because PdxMeshColor paints country colours automatically, recolouring a nation on a PdxMeshColor base often needs **no texture work**. Texture work is for new uniform patterns, insignia or fixed colours.
- New textures need a copy of the mesh whose material names them (Phase 2: re-export or patch). Verify on the first test unit.

## 5. Composition rules (confirmed)

- **States:** `idle`, `walk`, `attack`, `retreat`. `death` and `extra_state_1–3` are commented out in every vanilla unit entity. Do not template them.
- **State → animation id → type → file.** `state = { name = "idle" animation = "idle" }` names an **id** in the entity's pdxmesh (`animation = { id = "idle" type = "rifleman_idle_animation" }`). The type resolves through `animation.asset` to an `.anim` file.
- **Infantry pdxmesh animation ids (all 11 always defined in vanilla):** `idle walk attack death retreat` (on foot), `horse_idle horse_walk horse_attack horse_death horse_retreat` (as a cavalry rider), `artillery_attack` (as artillery crew). The generator always emits all 11. **UNVERIFIED:** how `artillery_attack` is triggered on the crew.
- **Infantry:** root entity = infantry pdxmesh. Weapon attach node depends on the weapon: **melee on `Right_hand_node`** (halberd), **muskets on `Left_hand_node`**.
- **Cavalry:** root entity = **horse** pdxmesh (`cavalry_horse` for tiers 1–2, `cavalry_horse_3_mesh` for tiers 3–4 in western). Horse states use ids `horse_idle`, `horse_walk`, `horse_attack`, and `retreat` → `horse_walk`. It carries `attach = { name = "rider" Saddle_Node = "<rider entity>" }`.
  The **rider** entity uses a pdxmesh for the **same `.mesh` file as that tier's infantry**. Sometimes the rider's pdxmesh is the same one the infantry uses, and sometimes it's a separately named pdxmesh for the same file (DAN tier 2: entity `DAN_INFANTRY_2` uses pdxmesh `western_generic_02_type1`, while `DAN_CAVALRY_2_rider` uses pdxmesh `DAN_INFANTRY_2`; both point to `western_generic_02_type1.mesh`). The rider's states use the `horse_*` ids, and it attaches its weapon with `Right_hand_node` (`cavalry_saber`).
- **Artillery:** root = `artillery_base_mesh`, a placeholder plane whose only purpose is two bones, `infantry_node` and `cannon_node`. It carries `attach = { name = "gunman" infantry_node = "TAG_INFANTRY_n" cannon_node = "<gfx>_ARTILLERY_n_cannon" }`. **Artillery depends on infantry**: a bad infantry name breaks artillery too. The cannon entity (`artillery_mesh`) fires its muzzle effect from a state event on locator `cannon_muzzle`.
- **Weapon effects:** `state = { name = "attack" event = { time = 0.90 node = "muzzle" particle = "musket_muzzle" } }` on the weapon entity. `node` is a locator in the weapon's mesh (`muzzle`, `trigger`).
- **Skeletons** (bone names in `base_models.json`):
  - western infantry: 28 bones, the same in all 6 western/DAN infantry mesh files (8 pdxmesh names). Attach bones `Right_hand_node`, `Left_hand_node`, plus unused `attach_back`, `attach_free`. Locators include `L/R_attach_hand_ctrl`.
  - horse: 30 bones, the same in both horse meshes. Attach bone `Saddle_Node`.
  - artillery base: `root`, `infantry_node`, `cannon_node`.
  - cannon: `Root`, `Cannon`, `wheels`; locator `cannon_muzzle`.
  - Bone **parenting** (hierarchy) is deferred to Phase 3 (Blender import via io_pdx_mesh).

## 6. error.log signatures (validator must pre-empt)

Log path: `Documents/Paradox Interactive/Europa Universalis IV/logs/error.log`

| Log line | Meaning | Validator rule |
|---|---|---|
| `Failed to find entity "X" for attachment in gunman` | Artillery crew/attach target missing | Every attach target resolves |
| `Failed to find entity "..." for attachment` | Weapon/rider entity missing (often absent DLC asset) | Same; flag DLC-only targets |
| `Set a higher version on entity X` | Duplicate name, version collision | Scan vanilla + DLC + mod for name clashes |
| `Could not find mesh file gfx/models/...mesh` | pdxmesh `file =` wrong | Every pdxmesh file exists (mod, vanilla or DLC) |
| Black/untextured model in-game | Textures in .mesh missing or wrong format | Mesh texture refs resolve in the mesh's folder; DDS format matches base |
| (no log; frozen/T-posed unit) | State names an animation id the pdxmesh lacks | Every state animation id exists in the resolved pdxmesh; every type exists; rider pdxmesh has `horse_*`; crew pdxmesh has `artillery_attack` |

## 7. Templates

`hr_` and `MAC` are placeholders; the prefix and tag are configurable. Generated entities always carry the project `version`.

### 7.0 Phase 1 form (no new meshes)
Phase 1 entities point at **vanilla pdxmeshes** by name and define no pdxmesh or animation blocks. A TAG infantry entity is a full entity, the way vanilla `DAN_INFANTRY_2` is:
```
# gfx/entities/hr_mac_units.asset
entity = {
    name = "MAC_INFANTRY_2"
    pdxmesh = "western_generic_02_type1"
    version = 20
    state = { name = "idle"    animation = "idle" }
    state = { name = "walk"    animation = "walk" }
    state = { name = "attack"  animation = "attack" }
    state = { name = "retreat" animation = "retreat" }
    attach = { Left_hand_node = "western_musket" }
}
```
Cavalry and artillery use the clone forms in 7.2 and 7.3.

## 8. Architecture

```
pyproject.toml          # package + pytest config (pythonpath = src)
src/eu4unitgen/
  core/
    project.py        # mod root, vanilla path, DLC path, owned DLC, target EU4 version
    nation.py         # tag, gfx culture, colours, tech group, tier→era mapping
    naming.py         # single source of truth for all generated names
  pdxscript/
    parser.py         # Clausewitz text parser/writer (recursive descent; must round-trip)
    templates/        # Jinja2: entity.asset, pdxmesh.gfx, sprite_pack.txt, gfx_sprite_pack.txt, pack_order.txt, unit.txt, loc.yml, country snippet
  library/
    base_models.json  # generated by scanner.py; see below
    scanner.py        # indexes the user's vanilla install + DLC zips in place; builds base_models.json
  textures/
    dds.py            # header read (FourCC, size, mips), write via Pillow or texconv
    recolour.py       # spec-mask painting, diffuse pattern overlays, gloss presets
  blender/
    runner.py         # subprocess: blender --background --python job.py -- args.json
    jobs/             # import_mesh.py, retarget_textures.py, kitbash.py, render_thumb.py, export_mesh.py
  validate/
    graph.py          # dependency graph: pack → entity → pdxmesh → mesh → textures; state id → anim type → .anim; attaches
    rules.py          # naming, missing nodes, version collisions, DDS format, loc keys, tech enables, anim ids, pack-order shadowing
    errorlog.py       # parse error.log after a test launch, map lines back to generated files
  export/
    writer.py         # dry-run diff, atomic writes, manifest of generated files
  gui/                # PySide6: Project setup, Nation wizard, Template picker, Texture editor, Validator, Export
tests/
```

### library/scanner.py
- Reads the base game and `dlc/*/*.zip` in place (stdlib `zipfile`). Path lookups ignore case, because scripts write `Units` and `units` interchangeably and Linux is case-sensitive.
- Indexes entities (`gfx/entities`), pdxmeshes (`interface/**/*.gfx` → `objectTypes`), animation types (`gfx/models/**/*.asset`), sprite packs, pack order, the graphical-culture list, `mil.txt` sprite levels and the game version. Every definition records its source file and DLC, so later validator rules can detect version collisions.
- Parses binary `.mesh` files (shader, texture names, bone names, locators with parent bone) and DDS headers.
- The Clausewitz reader inside scanner.py is a stopgap. Phase 1 swaps it for `pdxscript.parser`.
- CLI: `python -m eu4unitgen.library.scanner --eu4 "<install>" [--tag DAN] [--gfx westerngfx] [--no-dlc] [--out ...]`, or set `EU4_PATH`.
- Files in the `dlc/` folder don't prove the user owns that DLC (Steam installs them all), so DLC ownership is a project setting.

### base_models.json (schema_version 2)
Metadata only: names, paths, bone names, header facts. No game files or script text.
- `reference_nation`: the base-game chain for one tag (default DAN): sprite pack, per-tier composition, and `dlc_overrides` (DLC packs listing that tag's entities, their order, triggers, partial tiers, and redefined entities with versions).
- `graphical_culture_defaults`: the same for the gfx culture's pack.
- `recolour_bases`: per tier, the generic gfx-culture pdxmesh for infantry, horse, rider and cannon, each with `uses_country_colour`. This is the default base for recolour and kitbash.
- `pdxmeshes`: file, scale, `shader`, `uses_country_colour`, texture names + dir, skeleton id, locators, animation id → type map.
- `skeletons`, `animation_types` (with `file_exists`), `entities` (raw fields, including clone), `textures` (DDS headers), `sprite_levels`, `graphical_cultures`, `game_version`.

### Stack decisions
- **Python + PySide6**: same language as bpy/io_pdx_mesh, cross-platform Qt, LGPL.
- **Pillow ≥ 11.2.1** writes DXT1/DXT3/DXT5/BC2/BC3/BC5 via `im.save("x.dds", pixel_format="DXT5")`.
- **texconv** (optional, Windows): `texconv -ft DDS -f BC3_UNORM in.png` gives better quality and a full mip chain. Linux fallback: Compressonator or ImageMagick.
- **Blender** only as a subprocess. Pin Blender + io_pdx_mesh versions in settings. Known addon issues: animation export errors, custom normals ignored on re-export, `No module named 'imp'` on newer Blender.
- **3D preview**: Blender-rendered thumbnails (no custom renderer in MVP).
- **License**: GPL-3.0.

### Mesh approaches (ranked)
1. Entity clone / re-point (no mesh work). Covers all 12 slots immediately.
2. Texture swap/recolour on a copy of a base mesh (default base: `recolour_bases`), re-exported to point at new DDS files.
3. Kitbash in headless Blender: attach pre-weighted accessories (helmets, shields) to vanilla skeleton bones, then export.
4. Procedural variants on the same armature (needs human QC).
5. New rigged models: out of scope.

Edited meshes keep the vanilla skeleton, so they **reuse vanilla animation types**. io_pdx_mesh preserves armature structure on import/export.

## 10. Roadmap

### Phase 0: Ground truth — DONE (2026-10-14)
- EU4 install: `D:\Program Files (x86)\Steam\steamapps\common\Europa Universalis IV` (1.37.5).
- Reference nation: **DAN** (base game, westerngfx). Full chain recorded in `base_models.json` by `library/scanner.py`, with pytest coverage (synthetic fixtures, plus a regeneration check against the real install when `EU4_PATH` is set).
- The user **owns the Scandinavian unit pack (dlc116)**. In-game, `dlc116_DAN_sprite_pack` (order 100, `primary_culture = danish`) and `version = 4` entities replace DAN's base-game tiers 1, 3 and 4. Tier 2 isn't in that pack, so it stays base game. Don't use DAN or Danish-culture countries as a generated test nation, except on purpose as a known pack-priority/version case.
- Corrections to the original spec, now written into the sections above:
  1. pdxmeshes live in `interface/assets/*.gfx` → `objectTypes` (§2).
  2. Animation indirection: state → id → type → `.anim` (§2, §5).
  3. States are `idle walk attack retreat`; no `death` (§5).
  4. Muskets on `Left_hand_node`, melee on `Right_hand_node` (§5).
  5. Riders use a pdxmesh for the tier's infantry `.mesh` and need the `horse_*` ids; crew needs `artillery_attack` (§5).
  6. Vanilla entities have no `version`; DLC uses `version = 4` / `-1` (§3).
  7. `graphicalculturetype.txt` is a bare name list (§3).
  8. gfx-culture defaults are wired by a `graphical_cultures` sprite pack (§3, §7.4).
  9. Pack-order entries are optional (default 0); the generator still writes one for tag packs (§3).
  10. Normal maps are DXT1; diffuse DXT1; spec DXT5 (§4).
  11. Some nation meshes are PdxMeshStandard; recolour bases default to the generic meshes (§4).
  12. Sprite tiers confirmed at MIL 0/12/21/26 (§2).
- Moved out of Phase 0: bone **parenting** (hierarchy) is deferred to Phase 3. The Blender import of one infantry, horse+rider and artillery mesh moves with it; bone names, locators, shaders, texture names and DDS headers are already done.

### Phase 1: Scaffolder + validator (no meshes)
- Clausewitz parser/writer with round-trip tests on vanilla files; replace the stopgap reader in `scanner.py`.
- `naming.py`, Jinja2 templates, nation wizard (GUI).
- Generate: clone-based 12 TAG entities; gfx-culture default set; **TAG sprite pack and gfx-culture sprite pack (`graphical_cultures` block)**; pack-order entry for the TAG pack; `graphicalculturetype.txt` (vanilla list + new names, at export); units; mil.txt enables; localisation; country snippet.
- Validator: dependency graph, missing nodes, version collisions (vanilla + DLC + mod), orphan entities, missing loc keys, state animation ids, pack-order shadowing.
- Export with dry-run diff + manifest.
- **Done when:**
  - a nation generated by the app shows correct models in all 4 tiers in-game with a clean error.log;
  - **in-game test of fallback order and pack priority** is done and §3's UNVERIFIED items are resolved:
    - Fallback: (a) a tag with no sprite pack and no TAG entities; (b) a tag with `TAG_*` entities but no pack; (c) a tag whose gfx culture has only a gfx pack. Record which models show.
    - Priority: two packs for the same tag with different entities at orders N and N+1, then swapped. Record which wins. DLC116 + DAN is a second, free check (order 100, `version = 4`).

### Phase 2: Texture pipeline
- DDS read/write, spec-mask painter (R/G/B = country colour regions, A = gloss presets), diffuse pattern overlays.
- Blender job to copy a base mesh (from `recolour_bases`) and re-point its material to new textures.

### Phase 3: Blender mesh jobs
- Headless import/export, kitbash of pre-weighted accessories, thumbnail rendering for GUI preview.
- Import one vanilla infantry, horse + rider and artillery mesh via io_pdx_mesh; record **bone parenting** into `base_models.json` (scanner or a Blender job).

### Phase 4: Test loop
- "Launch & check": run EU4 with the mod, parse error.log, map errors back to generated files in the GUI.

### Phase 5+: Extensibility
- "Asset family" plugin model: entity templates + slot schema + validator rules.
- Ships: same entity/pdxmesh chain, but `sprite_level` (1–5) lives on the ship unit and ships don't auto-upgrade with tech.
- Portraits and cities: separate subsystems (2D sprites; graphical-culture building sets). Keep `naming.py` and `graph.py` generic.
